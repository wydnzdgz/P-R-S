# PLT 参数可运行范围评估

2026-11-17 Workspace 迁移说明：本文源码链接与复测命令已适配独立 `plt` package；历史 JSON、数值与源码指纹保持原样，见[迁移记录](workspace_migration.md)。

日期：2026-11-17。

本轮按已确认的用途开展：**PLT 自身需要承担门限不可伪造性；先评估本机可运行范围，不设具体安全位数。**

共登记 19 个参数点：10 个完成流程和额外数值诊断，2 个完成算法流程但诊断超时，4 个在发行部分陷门期间超时，3 个超过预设维度预算而跳过。
对完成流程的 12 个点，公开 LLL + 最近平面筛查均构造出了满足同余式和接受范数界的原像，无需陷门或份额。因此，**本轮找到了可运行范围，没有找到可批准承担门限不可伪造性的参数。B3 仍未通过。**

## 1. 实验范围与测量口径

- 环境：WSL2 / Linux x86_64，Intel i7-12700，20 个逻辑 CPU；Rust/Cargo 1.99.1。详细环境和源码 SHA-256 在 [扫描快照](plt_parameter_exploration_results.json)。
- 优化构建，每点独立新进程、独立新密钥。逐点串行执行，每点墙钟预算 30 秒，地址空间上限 1,024 MiB，原像维度上限 1,024。
- 每点向全部 k 人发行部分陷门，在集合 `{0,...,t-1}` 上进行 3 次随机目标的完整在线流程。本轮不重新遍历全部集合；集合全覆盖见 A 类测试。
- 记录 Setup、全部 k 次 PTrapGen 的耗时之和、单份 PSampPre、带检查 Rec、t 人串行在线流程、首位参与者的额外数值诊断，以及进程峰值 RSS。
- 编译不计入测量；各算法计时不包含 JSON 检查点输出。墙钟预算则包含诊断、公开攻击筛查和输出。
- 表中均值只来自一套密钥和 3 次在线流程，用于寻找工程运行边界，没有置信区间，不能替代正式性能实验。

新参数的 3 次输出仅用于流程检查；本轮没有重做 B4 的重复采样分布实验。既有 B4 结果仍只支持其原先登记的参数范围。

统一使用现有 `Setup/PTrapGen/PSampPre/Rec`，没有为不同门限另写算法，也没有放宽范数或数值拒绝条件。
令 `q31=2147483647`，`q61=2305843009213693951`，均为素数。尺寸仍由配置推导：

```text
ell = ceil(log2(q))
m = n*(ell+1)
A: (n*t) × D,  U_j: D × m,  D = 2*m*t
```

在线宽度使用所有已发行部分陷门的 `minimum_sigma_squared` 最大值，沿用现有保守 Frobenius 范数界；每点精确 sigma²、beta² 和发行采样宽度都保存在快照中。
这类依赖实际秘密对象的宽度选取与论文固定参数实例化之间的差异仍需处理。

这些数据支持先在较小实例上开发和计时，并提示后续需要分析矩阵计算、缓存和保守宽度的成本；不支持外推到车载硬件或端到端认证延迟。

## 3. 参数筛查与公开反例

### 必要条件通过仍不代表不可伪造

与 [论文作者公开版](https://olapiha.github.io/assets/pdf/TTrap.pdf) 第 3.5 节、Table 2 对照，本轮完成流程的较大模数点均通过了已编码的必要检查：
发行宽度平方不超过 `q²/m`，且 `m>k`。默认 q=257 两点仍违反发行宽度上界。
这些检查没有覆盖陷门/公钥均匀性、平滑误差预算、完整宽度条件和困难性实例化。
也没有把基本 SIS 的估计直接当作论文带部分陷门信息的安全估计。

只检查 `beta² < nt*floor(q/2)²` 会漏掉攻击：它只排除了“所有稀疏公开消元解都必然被接受”的充分条件。
在本次 n=1、q31、2-of-3 点，64 次随机列顺序消元没有找到接受解，但枚举全部 8,128 个可逆双列子矩阵后，有 **21 个**解通过方程和范数检查。
n=1、q61 的双列枚举没有找到接受解，仍不能据此认定困难。
枚举的计数与最小见证在 [双列筛查快照](plt_public_pair_screen_results.json)。

### LLL 与最近平面筛查

[公开筛查程序](../crates/plt/examples/plt_public_lattice_screen.rs) 只向求解函数传入 A 和 y：

1. 取最多 `2nt+8` 个公开列，用可逆的前 nt 列构造该子矩阵的模核整数格基。
2. 调用已锁定 qfall-math 的 LLL（delta=99/100，eta=501/1000）。
3. 在公开特解所在陪集中，用精确有理 GSO 和最近平面舍入得到较短的整数解。
4. 重新验证同余式，比较精确范数与原接受界；Python 再独立核验保存的整数见证。

本次 12 个完成流程点全部找到接受解。部分例子：

完整整数见证、目标来源、输入文件哈希及筛查源码哈希见 [公开格筛查快照](plt_public_lattice_screen_results.json)。
两个诊断超时点使用保存的第一个在线目标，其余使用公开消元筛查的随机目标；求解函数均不读取合法原像或任何秘密。
这只是对所测实例的具体反例，没有进行安全位数估计，也没有攻击满足适用条件的原论文构造。

**本轮范围内应继续保留协议参数拒绝状态。** 后续选参需要同时处理较低的公开方程维度、过宽的接受界、论文实例化条件和运行开销，单独提高 q 没有解决问题。
应在替换宽度界或优化实现之前说明参数依据，并重新进行公开求解筛查；不应通过缩窄接受界使合法采样频繁失败来掩盖问题。

## 4. 复测

以下命令默认把新实验写到 target，不覆盖文档中的历史快照：

```bash
python3 scripts/sweep_plt_parameters.py
cargo run --locked -p plt --release --example plt_public_lattice_screen -- \
  target/plt_parameter_exploration.json target/plt_public_lattice_screen.json
python3 scripts/verify_plt_parameter_exploration.py \
  target/plt_parameter_exploration.json \
  --lattice-screen target/plt_public_lattice_screen.json \
  --exhaustive-pairs-output target/plt_public_pair_screen.json
```

只测单点、修改运行预算或增大在线样本数：

```bash
python3 scripts/sweep_plt_parameters.py \
  --case n2_q2147483647_3of5 --trials 10 --timeout-seconds 60
```

直接核验当前历史快照：

```bash
python3 scripts/verify_plt_parameter_exploration.py \
  docs/plt_parameter_exploration_results.json \
  --lattice-screen docs/plt_public_lattice_screen_results.json
python3 -m unittest discover -s scripts -p 'test_parameter_screens.py'
```

扫描脚本保留超时、报错与跳过项；临时检查点只用于定位进度。扫描最多每 50 ms 观察一次 RSS，快速进程使用其自报峰值补足。
静态内存估计仅统计指定系数或单个 f64 方阵的载荷，不包括大整数、有理数、复制和分配器开销，不能用它替代实测 RSS。
